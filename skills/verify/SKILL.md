# verify — проверка кода и приложения

> Черновик v1. Команды помечены как `<F00>`: уточняются после F00, когда появятся реальные скрипты. Путь размещения скилла и формат подключения в Antigravity уточняем на шаге настройки.

## Принципы

1. **Доказательства, а не уверенность.** «Должно работать» не результат. Результат это вывод команд и наблюдаемое поведение в реальном приложении.
2. **Проверяй настоящий артефакт.** Юнит-тесты не заменяют запуск приложения. Для UI открой приложение и пройди сценарий.
3. **Проверка циклична.** Нашёл проблему: исправь, затем перезапусти **всё затронутое**, а не только упавшее.
4. **Честность.** Всё, что не удалось проверить, перечисли в отчёте с причиной. Нельзя писать «проверено», если не запускал.
5. **Не ослабляй проверки.** Запрещено удалять, пропускать (`skip`, `only`, `fixme`) или ослаблять тесты, отключать lint-правила и ослаблять типы, чтобы получить зелёный результат.
6. **Не выходи за скоуп.** Обнаруженные проблемы вне текущей задачи записывай в отчёт, не исправляй.

## Вход

- Текущая задача (`Fxx`, `Tn`) и спека `docs/feature-specs/<Fxx-...>.md` (acceptance criteria, test plan).
- Список изменённых файлов: `git status` и `git diff`.

## Шаги

### 0. Определи область

По diff определи, что затронуто: domain, repository, rules, hooks, UI, i18n, зависимости, конфиги. От этого зависит, какие шаги обязательны (см. матрицу внизу).

### 1. Статические проверки (всегда)

Запусти по очереди и сохрани вывод:

```
pnpm typecheck
pnpm lint
pnpm build
```

`<F00>`: подтвердить точные команды. Любая ошибка или предупреждение в изменённых файлах подлежит исправлению.

### 2. Unit и компонентные тесты (всегда)

```
pnpm test
```

Убедись, что для задачи есть тесты из test plan спеки и они **действительно проверяют поведение** (упали бы на сломанной реализации). Проверь негативные и граничные случаи.

### 3. Данные и правила (если затронуты repository, схемы, rules, балансы)

```
pnpm test:integration
pnpm test:rules
```

Проверь: баланс меняется атомарно с транзакцией, невалидные данные отклоняются правилами, чужой пользователь не имеет доступа. Если менялся `firestore.rules`, убедись, что изменены и rules-тесты, и `docs/02-data-model.md`, и что изменение было согласовано.

### 4. Реальный прогон приложения (если затронут UI или поведение в браузере)

1. Подними эмуляторы и dev-сервер (`pnpm emulators`, `pnpm dev`) `<F00>`.
2. Пройди сценарии из acceptance criteria **в браузере** (через Playwright или браузерный инструмент агента). Для каждого сценария зафиксируй результат.
3. Запусти релевантные e2e: `pnpm e2e` (или выбранный набор).
4. Посмотри консоль браузера: ошибки, предупреждения React, необработанные промисы, `permission-denied`, отсутствующие индексы, предупреждения i18n о пропущенных ключах.

### 5. Чеклист состояний и окружений (если UI)

Для каждого затронутого экрана отметь проверенное:

- [ ] loading (скелетон), empty (с действием), error (с повтором), offline, success (toast)
- [ ] mobile (360 px) и desktop (≥ 1024 px), нет горизонтального скролла страницы
- [ ] светлая и тёмная тема, читаемость и контраст
- [ ] EN и RU, длинные русские строки не ломают вёрстку, плюрали корректны
- [ ] клавиатура: порядок фокуса, видимый фокус, `Esc` в диалогах, aria-подписи у иконок-кнопок
- [ ] StrictMode: нет двойных подписок и утечек (подписки отписываются)

### 6. Проверка архитектуры и качества кода (всегда, по diff)

Проверь команды и поиском по diff:

- `firebase/firestore` не импортируется вне разрешённых файлов.
- Фичи импортируют друг друга только через `index.ts`, нет циклов.
- Нет жёстких строк в JSX (включая `aria-label`, `placeholder`, `title`).
- Нет `#hex`, `rgb()`, `bg-[#...]`, inline-style; цвета через токены.
- **DRY:** нет дублирования стилей, текстов, логики. Нет копий того, что уже есть в `components/common`, `lib`, хуках. Повторяющиеся наборы классов вынесены в компонент или `cva`.
- Размеры: компоненты ≈ до 150 строк, функции ≈ до 40; нет магических значений.
- Деньги: нет `float`, `toFixed` в расчётах. Даты транзакций: нет `Date`. Нет `null` в записываемых документах.
- Нет `any`, необоснованных `as`, `!`, `@ts-ignore`, `enum`, `export default` (кроме разрешённых).
- Нет `console.log`, закомментированного кода, `TODO` без ссылки.
- Нет legacy-паттернов из `AGENTS.md`, раздел 11.
- Нет изменений в зависимостях, конфигах, rules, индексах, CI без согласования.

### 7. Сверка с acceptance criteria

Пройди **каждый** AC спеки. Для каждого: выполнено или нет, чем доказано (тест, команда, сценарий в браузере).

### 8. Цикл исправления

Если что-то не прошло:
1. Опиши проблему и первопричину.
2. Исправь минимально в рамках задачи.
3. Перезапусти все затронутые шаги (не только упавший).
4. Повторяй до зелёного или до явного блокера. Блокер опиши в отчёте.

## Матрица: какие шаги обязательны

| Что изменено | Шаги |
|---|---|
| Только domain (`lib/*`) | 1, 2, 6, 7 |
| Repository, схемы, баланс | 1, 2, 3, 6, 7 |
| `firestore.rules` | 1, 2, 3, 6, 7 (+ ADR и `02-data-model.md`) |
| UI, страницы, компоненты | 1, 2, 4, 5, 6, 7 |
| i18n | 1, 2, 5, 6, 7 |
| Конфиги, зависимости, CI | 1, 2, 6 (+ подтверждение, что изменение согласовано) |
| Перед релизом (F13) | Все шаги + Lighthouse и a11y-проход |

## Формат отчёта

Выведи отчёт **в конце**, в таком виде:

```
## Verify: <Fxx-Tn> — <краткое название>

**Итог:** PASS | FAIL | PARTIAL

### Выполнено
| Проверка | Команда или способ | Результат |
|---|---|---|
| typecheck | pnpm typecheck | ok |
| lint | pnpm lint | ok |
| unit и component | pnpm test | 42 passed |
| rules | pnpm test:rules | ok (если применимо) |
| build | pnpm build | ok |
| e2e / ручной прогон | сценарий, шаги | ok / найдено: ... |

### Acceptance criteria
- AC1: ✅ доказано тестом `...`
- AC2: ✅ проверено в браузере (шаги: ...)
- AC3: ❌ причина ...

### Не проверено (и почему)
- ...

### Найдено вне скоупа (не исправлялось)
- ...

### Исправлено в ходе проверки
- ...
```

## Запрещено

- Сообщать «готово» без запуска шагов 1–2 и шагов, обязательных по матрице.
- Помечать пункт проверенным, если он не выполнялся.
- Править спеку, тесты или правила линтера, чтобы подогнать результат.
- Запускать проверки против боевых проектов Firebase (только эмуляторы).
