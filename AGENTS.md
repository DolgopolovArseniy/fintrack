# FinTrack — трекер личных финансов

> Рабочее название: **FinTrack** (меняется один раз, в F00).
> Этот файл загружается в каждую сессию. Он короткий намеренно: подробности лежат в `docs/`.
> Если инструмент (Antigravity CLI) читает другой файл (например `GEMINI.md`), он должен быть тонкой ссылкой на этот. Проверяется при настройке.

## 1. Что это

SPA без собственного бэкенда: React + TypeScript + Firebase (Auth + Firestore). Проект для портфолио фрилансера, поэтому важны качество кода, безопасность, UX и тесты, а не количество экранов.

## 2. Стек

React 19, TypeScript (strict), Vite, Tailwind CSS v4, shadcn/ui (Radix, lucide), React Router (data router), React Hook Form + Zod, Firebase modular SDK (Auth + Firestore), Recharts, date-fns, PapaParse, i18next, Vitest + Testing Library, Playwright, `@firebase/rules-unit-testing`, ESLint (flat), Prettier, pnpm.

Точные версии фиксируются в F00 (таблица в `docs/01-architecture.md`, §2). Не обновляй версии без согласования.

## 6. Рабочий процесс

- Сначала прочитай спеку фичи. Потом план. Потом код. Одна задача (T1, T2…) за сессию, один коммит.
- Не выходи за рамки задачи и списка файлов из спеки. Замеченные проблемы вне задачи записывай в конец ответа, а не чини «заодно».
- **Спросить, а не угадывать:** если спека неоднозначна или ты не уверен в API, остановись и задай вопрос.
- **Без согласования не меняй:** зависимости (`package.json`), конфиги (Vite, TS, ESLint, Firebase), `firestore.rules`, `firestore.indexes.json`, CI, `.env.example`.
- Перед сообщением «готово» пройди раздел 10 (верификация).
- Честно сообщай, что **не** проверял.

## 7. Архитектурные правила (подробности: `docs/01-architecture.md`)

- Слои: UI → Hooks → Repositories → Firebase SDK. Domain (`src/lib`) содержит чистые функции без React и Firebase.
- `firebase/firestore` импортируется **только** в `features/*/repository.ts`, `lib/firebase.ts` и `lib/firestore/*`.
- Фичи импортируют друг друга **только** через `index.ts` (публичный API фичи). Циклических импортов нет.
- `lib/` не знает про `features/`. `components/ui` и `components/common` не знают про `features/`.
- Деньги: целые числа в minor units. Никогда float, никогда `toFixed` в расчётах.
- Дата транзакции: строка `YYYY-MM-DD`. Никогда `Date` для даты транзакции.
- Данные из Firestore валидируются Zod на границе (converter). Типы выводятся из схем (`z.infer`).
- Каждый `onSnapshot` отписывается в cleanup. Используй общий хук подписки, не пиши свой.
- В документах Firestore нет `null`: необязательное поле отсутствует (`deleteField()` при удалении).

## 8. Качество кода: maintainability и DRY (подробности: `docs/03-conventions.md`)

Код пишется для того, кто будет его читать и менять через полгода.

- **DRY без фанатизма.** Повторяется логика, текст или набор стилей: вынеси в одно место (функция, хук, компонент, вариант, токен, ключ i18n). Правило: **второе** повторение допустимо, **третье** обязательно выносится. Для стилей и строк выноси уже при втором.
- **Стили.** Одинаковый набор Tailwind-классов в двух и более местах означает отдельный компонент или вариант (`cva`). Нет длинных `className` «на месте»: они живут внутри компонента. Цвета только через токены темы, никаких `#fff`, `bg-[#...]`, inline-style.
- **shadcn-компоненты** в `components/ui` не правим без нужды. Расширяй обёртками в `components/common`.
- **Повторяющиеся UI-паттерны** (шапка страницы, пустое состояние, состояние ошибки, скелетон, сумма, навигатор месяца, подтверждение удаления, бейдж категории) существуют в `components/common` в единственном экземпляре. Перед созданием нового компонента проверь, нет ли такого там.
- **Одна ответственность.** Компонент до ~150 строк, функция до ~40. Больше значит разбей. Логика в хуках и `lib`, а не в JSX.
- **Нет магических значений:** числа, строки, лимиты, коды выносятся в константы с именем.
- **Не усложняй заранее.** Не создавай абстракцию под один случай. Не добавляй «на вырост» то, чего нет в спеке.
- Имена говорят о намерении. Комментарии объясняют «почему», а не «что».
- Перед написанием нового кода ищи существующий аналог в проекте и следуй ему (`features/categories` — эталонная фича).

Перед использованием любого API, в котором есть малейшая неуверенность, запроси актуальную документацию. Не полагайся на память: версии меняются.

## 10. Верификация

- Используй скилл **`verify`** (`skills/verify/SKILL.md`, команды уточняются в F00). Он определяет, как проверять код и приложение, и требует доказательств.
- До его появления минимум: `pnpm typecheck && pnpm lint && pnpm test && pnpm build`. Для UI дополнительно проверь руками на эмуляторах (loading, empty, error, offline, mobile, EN/RU, тёмная тема).
- Слова «должно работать» не считаются результатом. Результат это вывод команд и проверенное поведение.

## 11. Запрещено и устаревшие паттерны

Модели часто откатываются к устаревшим API. **Не используй:**

- Firebase v8/compat: `firebase.firestore()`, `firebase.auth()`, `firebase/compat/*`.
- Tailwind v3-стиль: `tailwind.config.js`, директивы `@tailwind base/components/utilities`. В v4 конфигурация живёт в CSS. Сверяй через Context7.
- React Router v5: `Switch`, `useHistory`, `Redirect`, `component=`. Используй API data router.
- Классовые компоненты, `defaultProps`, `forwardRef` (в React 19 `ref` это обычный проп), `React.FC`.
- `any`, `as` без обоснования, `!` без комментария, `@ts-ignore` (допустим `@ts-expect-error` с причиной), `enum` (используй union-типы и `as const`).
- `export default` (кроме случаев, когда этого требует фреймворк). Только именованные экспорты.
- `useEffect` для вычисляемых данных и для загрузки данных. `useEffect` с подпиской без cleanup.
- `Date` для даты транзакции, float для денег, `toFixed` в расчётах.
- Жёстко заданные строки в JSX, жёстко заданные цвета, inline-style, `console.log` в коммитах.
- Лишние зависимости: `moment`, `axios`, целиком `lodash`.
- Barrel-файлы (`index.ts`) вне публичного API фичи.

## 12. Definition of Done

Задача завершена, когда: acceptance criteria из спеки выполнены, есть тесты из test plan, `verify` пройден с доказательствами, нет нарушений разделов 7, 8 и 11, документация и статус в `docs/06-roadmap.md` обновлены, незавершённое и непроверенное явно перечислено.

## 13. Предотвращение зацикливаний и тяжелых команд (Anti-Loop & Performance)

- Запрещено выполнять одно и то же действие, запуск проверки или вызов инструмента более 2 раз подряд с одинаковым результатом. Если команда или тест завершились ошибкой дважды, остановись, проанализируй причину и смени подход.
- **Чтение файлов:** запрещено читать один и тот же файл мелкими кусками подряд. Если нужен контекст файла, читай его целиком за один вызов инструмента.
- **Покрытие тестами:** не пытайся маниакально добиться 100% coverage, если базовые ветки и краевые случаи уже покрыты (>85–90%). 2–3 непокрытые служебные строки не стоят десятка лишних итераций.
- **Режим планирования (/plan):** строго запрещено запускать терминальные команды проверки (`pnpm lint`, `pnpm test`, `pnpm build`, `tsc`). План составляется только на основе чтения файлов спецификаций и кода.
- **Команды в фоне:** не запускай длительные или интерактивные команды в фоне, блокирующие сессию. Все проверки запускаются синхронно только на этапе верификации.
- Запрещено запускать рекурсивный поиск файлов (`Get-ChildItem -Recurse`, `find`, `grep`) без жесткого исключения папок `node_modules`, `.git`, `dist`, `.emulator-data`. Поиск веди точечно по известным путям (`src/`, `docs/`).
- Запрещено уходить в пространные рассуждения (thought loops). Формулируй конкретное действие и сразу выполняй вызов инструмента.

## 14. Автономное выполнение задачи (Scope Execution)

- В рамках текущей задачи (например, T1 или T2) выполняй реализацию от начала до конца без пауз на промежуточные риторические вопросы.
- Ошибки линтера, сборки и тестов исправляй самостоятельно по ходу работы, доводя проверку до зелёного статуса.
- Остановка для вопроса пользователю допустима только при обнаружении неустранимого архитектурного противоречия или явной двусмысленности в бизнес-логике спеки.
