# ADR-0016: Границы ответственности Firestore Security Rules и отказ от get() / exists()

* **Статус**: Accepted
* **Дата**: 2026-10-03
* **Автор**: Senior Tech Lead / FinTrack Team

## Контекст и проблема

Cloud Firestore Security Rules исполняются на серверах Firebase перед каждой операцией чтения и записи. В FinTrack безопасность опирается на строгую изоляцию пользовательских путей (`users/{uid}/**`), белые списки полей, проверку типов данных, диапазонов и неизменяемости серверных временных меток (`createdAt`, `updatedAt`).

При проектировании валидации транзакций, счетов и бюджетов возникает вопрос проверки целостности ссылок и бизнес-согласованности:
1. Существуют ли `accountId` и `categoryId`, на которые ссылается транзакция?
2. Совпадает ли `type` транзакции (`expense` / `income`) с типом выбранной категории?
3. Соответствует ли баланс счёта сумме входящих и исходящих транзакций?
4. Является ли дата транзакции календарно корректной (например, `2026-02-31` формально соответствует регулярному выражению `YYYY-MM-DD`, но такой даты в календаре не существует)?

Для проверки ссылок и связанных документов в синтаксисе Security Rules существуют функции `get()`, `exists()` и `getAfter()`. Однако их использование в правилах влечёт жёсткие платформенные ограничения:
- Firestore ограничивает количество вызовов `get()` / `exists()` в правилах (до 10–20 обращений на транзакцию или batch-запрос).
- В FinTrack пакетный импорт CSV-транзакций выполняется чанками до 400 документов в одном batch (`IMPORT_CHUNK_SIZE = 400`). Использование даже одного `get()` или `exists()` в правиле транзакции приведёт к мгновенному падению пакетной записи из-за превышения квоты.
- Каждый вызов `get()` в rules тарифицируется как отдельная операция чтения и увеличивает сетевую задержку валидации.
- ADR-002 запрещает использование Cloud Functions на бесплатном тарифе Spark, поэтому валидация должна быть сбалансирована между клиентом и Security Rules.

## Рассмотренные варианты

1. **Проверка ссылочной целостности и соответствия типов в Security Rules через `get()` и `exists()`**
   - *Минусы*: Нарушает лимиты Firestore на обращения к документам в batch; блокирует пакетный импорт транзакций (400 операций за раз); увеличивает задержки и расходы на тарифицируемые чтения.
2. **Только структурная валидация и изоляция в Security Rules; целостность связей, согласованность баланса и календарная корректность дат на клиенте/репозитории (Выбранный)**
   - *Плюсы*: Отсутствие вызовов `get()` / `exists()` / `getAfter()` позволяет выполнять batch до 500 операций (в FinTrack используется безопасный чанк 400); нулевые накладные расходы на дополнительные чтения; минимальное время валидации правил; независимость подколлекций.
3. **Использование Cloud Functions для валидации и пересчёта**
   - *Минусы*: Запрещено ADR-002 (тариф Spark, отсутствие внешнего бэкенда).

## Решение

1. В `firestore.rules` **намеренно и осознанно исключены** любые вызовы `get()`, `exists()` и `getAfter()`. Это зафиксировано статическим тестом `rules-tests/sync.test.ts`.
2. **Зона ответственности Security Rules:**
   - Авторизация и изоляция: пользователь имеет доступ только к своим документам `users/{uid}/**` (`isOwner(uid)`).
   - Запрет по умолчанию для всех внешних путей, коллекций и подколлекций.
   - Защита схемы документов: строгие белые списки допустимых ключей (`hasExactKeys`), отсутствие лишних полей.
   - Валидация типов данных и диапазонов чисел (`isIntBetween`), длин строк (`isText`, `isOptionalText`), списков (`tags.size() <= 10`).
   - Синтаксическая валидация формата дат (`matches` по маске `YYYY-MM-DD` и `YYYY-MM`).
   - Контроль временных меток: `createdAt` и `updatedAt` обязаны равняться `request.time` при создании; `createdAt` неизменяем при обновлении, а `updatedAt` обязан обновляться сервером.
   - Составные идентификаторы документов: `budgetId == month + '_' + categoryId`.
   - Неизменяемость типа категории при обновлении (`incoming().type == existing().type`).
3. **Зона ответственности клиентского слоя (Repository + Zod + Domain lib):**
   - Проверка существования счёта и категории перед сохранением транзакции.
   - Проверка соответствия типа транзакции типу категории.
   - Календарная валидация дат через библиотеку дат (`date-fns` / Zod custom validator), отсекающая несуществующие даты вроде 31 февраля.
   - Расчёт и поддержание дельт баланса счетов в транзакциях и возможность полного пересчёта баланса счёта по журналу операций (`recalculateAccountBalance`).

## Последствия

### Положительные:
* Пакетный импорт 400 транзакций выполняется в одном атомарном batch без превышения квот Firestore по вызовам `get()`.
* Максимальная скорость работы и минимальная задержка при записи данных.
* Отсутствие лишних платных операций чтения документов при валидации правил.
* Поведение чётко задокументировано и зафиксировано unit-тестами правил в `rules-tests/transactions.rules.test.ts` и статическими проверками в `rules-tests/sync.test.ts`.

### Отрицательные / Компромиссы:
* Пользователь с прямым доступом к API Firestore в обход интерфейса FinTrack может записать транзакцию с несуществующим `accountId` или датой `2026-02-31`. Поскольку изоляция путей гарантирует, что пользователь может модифицировать только свои собственные данные внутри `users/{свой uid}`, данные других пользователей и безопасность системы в целом не компрометируются.
* В случае рассинхронизации баланса из-за некорректных записей целостность восстанавливается вызовом функции пересчёта баланса из репозитория.
