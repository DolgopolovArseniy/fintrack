# 05. Стратегия тестирования

Статус: draft v1

## 1. Цели

1. Деньги, даты, баланс и правила доступа работают **корректно и доказуемо**.
2. Агент не может незаметно сломать поведение: любое изменение проверяется автоматически.
3. Тесты быстрые и стабильные, чтобы их запускали постоянно.
4. Тесты служат документацией поведения и сильным пунктом портфолио.

## 2. Пирамида

| Уровень | Инструмент | Что проверяет | Доля |
|---|---|---|---|
| **Unit (domain)** | Vitest | `money`, `dates`, `aggregations`, `csv`, `balanceDeltas`, схемы Zod | Много, быстрые |
| **Integration (repository)** | Vitest + эмуляторы Firebase | Repository, converters, batch, баланс, запросы | Средне |
| **Rules** | Vitest + `@firebase/rules-unit-testing` | Security Rules (`02-data-model.md` §13) | Полный набор |
| **Component** | Vitest + Testing Library | Формы, списки, состояния, фильтры, `common`-компоненты | Средне |
| **E2E** | Playwright | Ключевые сценарии в браузере против эмуляторов | Мало, критичные |
| **A11y** | `@axe-core/playwright` | Доступность ключевых экранов | В составе e2e |

Принцип: проверяем на самом низком уровне, где это возможно. e2e не дублирует логику unit-тестов.

## 3. Что покрываем и как

### 3.1 Unit (domain)

Плотное покрытие, включая граничные случаи. Цель: **100% ветвей** для `money`, `dates`, `csv`, `balanceDeltas`, агрегаций.

| Модуль | Обязательные случаи |
|---|---|
| `money` | Парсинг ввода (`12.5`, `12,50`, `1 000,5`, пусто, мусор, отрицательное, слишком много знаков), округление, форматирование в EN и RU, нули, большие суммы, `signedAmount` |
| `dates` | Валидный и невалидный `YYYY-MM-DD` (30 февраля, високосный год), границы месяцев, диапазон месяца, сдвиг месяца (декабрь → январь), без зависимости от часового пояса (тесты запускаются в нескольких TZ) |
| `balanceDeltas` | Создание, удаление, смена суммы, смена типа, смена счёта, смена суммы и счёта одновременно, нулевая дельта |
| `aggregations` | Итоги по типу, по категориям, по месяцам, пустой набор, топ-N и «Другое» |
| `csv` | Экранирование кавычек, разделителей и переносов, CSV-injection (`= + - @`), BOM, разделитель `;` и `,`, парсинг, маппинг колонок, построчные ошибки, дубликаты |
| Схемы Zod | Валидные и невалидные входы, границы длины и значений |

### 3.2 Integration (repository, эмулятор)

- Запуск: `firebase emulators:exec` (или скрипт `pnpm test:integration`), чистая база перед каждым тестом.
- Проверяем: запись транзакции и изменение баланса в одном batch (успех и откат), редактирование, удаление, смена счёта, `recalculateAccountBalance`, converters (битый документ не роняет чтение), чанкинг импорта (400+ строк), онбординг-batch.
- Тесты работают с эмулятором, **не с боевыми проектами**.

### 3.3 Rules

- Полный набор из `02-data-model.md` §13 и спеки `F03-firestore-rules.md`. Обязательны «негативные» тесты: чужой пользователь, аноним, лишние поля, неверные типы, неверные даты, подмена `createdAt`, границы чисел и длин.
- Архитектура тестовой инфраструктуры:
  - Раннер: Vitest в окружении `node`, отдельный конфиг `vitest.rules.config.ts`, последовательный запуск файлов (`fileParallelism: false`) против общего эмулятора.
  - Каталог: `rules-tests/` в корне проекта (изолирован от основного прогона `pnpm test`).
  - Эмулятор: Firestore emulator в проекте `demo-fintrack-rules`, запускается через `firebase emulators:exec --only firestore ...` по скрипту `pnpm test:rules`.
  - Хелперы: `rules-tests/helpers/env.ts` (`initializeTestEnvironment`, контексты `ownerDb`, `otherDb`, `anonOwnerDb`, `guestDb`), `rules-tests/helpers/docs.ts` (билдеры валидных сырых документов с маркером `DELETE_FIELD`), `rules-tests/helpers/seed.ts` (запись исходных документов в обход правил через `withSecurityRulesDisabled`).
  - Очистка: `clearFirestore()` (`testEnv.clearFirestore()`) перед каждым тестом (`beforeEach`).
  - Статические и Sync-тесты: `rules-tests/sync.test.ts` (без обращения к эмулятору) проверяет синхронизацию белых списков валют/локалей, числовых границ из `lib/limits.ts`, запрет вызовов `exists()`/`get()` (ADR-0016), версию правил и совпадение текста правил в `02-data-model.md` с `firestore.rules`.
- Запускаются в CI в отдельном джобе `rules` с JDK 21. Изменение `firestore.rules` без изменения тестов в том же PR запрещено.

### 3.4 Component

- Запросы по роли и тексту (`getByRole`, `getByLabelText`), не по CSS-классам и не по `data-testid` без необходимости.
- Проверяем: форма (валидация, сообщения, отправка, фокус на ошибке), список (группировка по дням, пустое состояние), `QueryBoundary` (все ветки), фильтры, `MoneyText`, `AmountInput`, `MonthNavigator`.
- Repository и Firebase мокаются на границе hook/repository (функциями репозитория), не глубже.
- Тексты проверяем через i18n-ключи или реальные EN-строки, единообразно по проекту.

#### Инфраструктура E2E и эмуляторы (F02)
- Playwright запускает изолированные сервисы через массив `webServer`:
  1. Эмулятор Firebase Auth (`firebase emulators:start --only auth --project demo-fintrack`, порт `9099`).
  2. Dev-сервер Vite на отдельном порту `5174` с флагом `strictPort`, переменными `VITE_USE_EMULATORS=true` и `VITE_FIREBASE_PROJECT_ID=demo-fintrack`, чтобы избежать конфликта с локальным dev-сервером на 5173.
- Очистка состояния Auth-эмулятора между тестами: REST-эндпоинт `DELETE http://127.0.0.1:9099/emulator/v1/projects/demo-fintrack/accounts`.
- Проверка служебных писем (верификация email, сброс пароля): чтение REST-эндпоинта `GET http://127.0.0.1:9099/emulator/v1/projects/demo-fintrack/oobCodes`.
- В CI окружении: автоматическая установка JDK 21 (`actions/setup-java`) и кеширование бинарных файлов эмуляторов Firebase (`~/.cache/firebase/emulators`).

Правила: тесты независимы, данные создаются в начале теста (через эмулятор), никаких `sleep`, ожидания по состоянию (`expect` с auto-retry), один пользователь на тест.

## 4. Тестовые данные

- Фабрики в `src/test/` (`buildTransaction()`, `buildAccount()`, …) с переопределением полей. Объекты не копируются по тестам.
- Для e2e и demo: детерминированный сид (фиксированный seed генератора), чтобы результаты воспроизводились.
- Время фиксируется (`vi.setSystemTime`), тесты не зависят от текущей даты.

## 5. Качество тестов (обязательные правила)

- Тест проверяет **поведение**, падает при сломанной функциональности и проходит при рефакторинге.
- Нельзя: `it.skip`, `it.only`, `test.fixme` в коммитах, ослаблять или удалять тест, чтобы «позеленело» (агенту это запрещено явно).
- Баг сначала воспроизводится падающим тестом, затем исправляется.
- Один тест, одна причина падения. Имя описывает поведение.
- Нестабильный (flaky) тест считается багом: чиним или временно выносим с записью в задачу, не оставляем «перезапуск до зелёного».
- Покрытие это индикатор, не цель. Числовой порог ставим на domain-слой, остальное проверяем по осмысленности.

## 6. Запуск

| Команда | Что запускает | Когда |
|---|---|---|
| `pnpm test` | Unit и component | Постоянно, pre-commit (на изменённых) |
| `pnpm test:integration` | Repository на эмуляторе | Перед PR, в CI |
| `pnpm test:rules` | Security Rules | Перед PR, в CI |
| `pnpm e2e` | Playwright | Перед PR, в CI |

## 7. CI

Порядок: typecheck, lint, unit и component, rules и integration (с эмуляторами), build, e2e, preview-деплой. Артефакты e2e (trace, скриншоты, видео при падении) сохраняются. Merge только при зелёном CI.

## 8. Тесты в цикле работы агента

- Каждая задача в спеке включает test plan. Тесты пишутся **вместе** с кодом (часто первыми для domain).
- Агент запускает релевантные тесты после каждого изменения и перед сообщением «готово» проходит скилл `verify`.
- Ревью проверяет: есть ли тесты на acceptance criteria, есть ли негативные случаи.

## 9. Ручная проверка (дополнение, не замена)

Выполняется в `verify` и в F13: состояния UI, mobile и desktop, светлая и тёмная тема, EN и RU (длинные строки), клавиатура, offline, печать CSV в Excel (кириллица, `;`), Lighthouse.
