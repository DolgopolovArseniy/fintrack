# 03. Конвенции кода

Статус: draft v1 · Правила проверяются линтером и ревью. Примеры «хорошо/плохо» нормативны.

## 1. Принципы

1. **Читаемость важнее краткости.** Код читают чаще, чем пишут.
2. **Maintainability.** Изменение одного правила, текста, стиля или формулы происходит в **одном** месте.
3. **DRY, но не любой ценой.** Дублируем осознанно, пока повторение случайно. Выносим, когда повторяется смысл.
4. **Простота.** Не создаём абстракцию под один случай. Не пишем «на вырост» то, чего нет в спеке.
5. **Эталон.** Перед новым кодом найди аналог в проекте и следуй ему (`features/categories` эталонная фича, после её завершения).

## 2. Maintainability и DRY

### 2.1 Когда выносить

| Что повторяется | Когда выносить | Куда |
|---|---|---|
| Набор Tailwind-классов | **Второе** использование | Компонент или вариант `cva` |
| Строки интерфейса | Сразу | Ключ i18n (повторный текст использует один ключ) |
| Числа, лимиты, коды, названия | Сразу | Именованная константа |
| UI-паттерн (пустое состояние, шапка, диалог подтверждения) | Второе использование | `components/common` |
| Логика вычислений и преобразований | **Третье** использование | Функция в `lib/` или `utils.ts` фичи |
| Логика с состоянием или эффектами | Третье использование | Хук |
| Converter, подписка, пути коллекций | Сразу | `lib/firestore/`, `useSubscription` |
| Zod-правила валидации | Второе использование | Общая схема (`isoDateSchema`, `moneySchema`) |

**Повторение по совпадению** (два похожих куска, которые меняются по разным причинам) не выносим. Вопрос к себе: «если одно поменяется, второе обязано поменяться тоже?» Да означает вынести.

### 2.2 Стили и компоненты

- **Нет длинных `className` «на месте».** Если блок классов повторяется, он становится компонентом. Если отличается только вариантом (размер, цвет, тип), то `cva` с вариантами.
- **Только токены.** Цвета, радиусы, тени, отступы из темы (CSS-переменные shadcn). Запрещены `#hex`, `rgb()`, `bg-[#...]`, inline `style`. Произвольные значения вида `w-[37px]` только с комментарием-причиной.
- **Условные классы** собираются функцией `cn()`, не конкатенацией строк.
- **`components/ui` (shadcn)** не правим ради своих нужд. Расширяем обёрткой в `components/common` или вариантом. Правка допустима для общих исправлений и фиксируется в коммите.
- **Перед созданием компонента** проверь `components/common`. Если подходящий есть, используй. Если почти подходит, расширь его пропсом или вариантом, а не копируй.
- **Свойства компонента** типизируются, имеют разумные значения по умолчанию, не принимают «всё подряд» (`any`, `Record<string, unknown>`).

Плохо:

```tsx
<div className="flex items-center gap-2 rounded-lg border border-dashed p-8 text-center text-sm text-muted-foreground">
  <Inbox className="h-6 w-6" /> {t('transactions.empty')}
</div>
// ...то же самое, скопированное в budgets, accounts, categories
```

Хорошо:

```tsx
<EmptyState icon={Inbox} title={t('transactions.empty.title')} action={<AddTransactionButton />} />
```

### 2.3 Размеры и ответственность

- Компонент до ~150 строк, функция до ~40, файл до ~300. Превышение означает разбить.
- Компонент отвечает за **отрисовку**. Логика данных в хуках, вычисления в `lib`.
- У функции один уровень абстракции и одна причина меняться.
- Вложенность `if` не более двух уровней. Используем ранний `return` (guard clauses).
- Параметров не более 3–4. Больше означает объект параметров.

### 2.4 Чего не делаем во имя «чистоты»

- Не создаём «универсальный» компонент с 15 пропсами ради двух случаев.
- Не создаём `utils.ts` «на свалку». Функция живёт рядом с тем, кому принадлежит.
- Не оборачиваем каждую мелочь в хук или контекст.

## 3. TypeScript

- `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`. Включено в F00, не ослабляется.
- **Запрещены:** `any`, необоснованное `as`, `!` без комментария, `@ts-ignore` (допустим `@ts-expect-error` с причиной), `enum`.
- Union-типы и `as const` вместо enum. Результат работы с неопределённостью через сужение типов.
- Типы доменных объектов выводятся из Zod (`z.infer`), не дублируются вручную.
- `unknown` на границах (ошибки, JSON, данные Firestore), дальше сужается парсингом.
- Именованные экспорты. `export default` только если этого требует фреймворк.
- `type` для объединений и алиасов, `interface` для расширяемых контрактов объектов (последовательно по проекту, выберем один стиль в F00 и зафиксируем в ESLint).

Плохо: `const tx = doc.data() as Transaction`
Хорошо: `const tx = transactionSchema.parse({ id: doc.id, ...doc.data() })` (внутри converter)

## 4. Именование

| Что | Стиль | Пример |
|---|---|---|
| Файлы компонентов | `PascalCase.tsx` | `TransactionForm.tsx` |
| Файлы хуков, утилит, lib | `camelCase.ts` | `useTransactions.ts`, `money.ts` |
| Папки | `kebab-case` | `import-export/` |
| Компоненты, типы | `PascalCase` | `MonthNavigator`, `TransactionInput` |
| Функции, переменные | `camelCase` | `parseMoneyInput` |
| Константы | `UPPER_SNAKE_CASE` | `MAX_AMOUNT` |
| Хуки | префикс `use` | `useCreateTransaction` |
| Булевы | `is`, `has`, `can`, `should` | `isArchived` |
| Обработчики | `handleX` (внутри), `onX` (пропсы) | `onSubmit`, `handleDelete` |
| Ключи i18n | `feature.section.key` | `transactions.form.amountLabel` |
| Ветки | `feat/F05-transactions`, `fix/...` | |
| Коммиты | Conventional Commits, английский | `feat(transactions): add month navigator` |

Имя отвечает на вопрос «что это». Без сокращений вроде `tx` в публичных API (допустимо в коротких локальных областях), без `data`, `info`, `handle` без контекста.

## 5. React

- Только функциональные компоненты и хуки. `ref` передаётся как обычный проп (React 19).
- **Производные данные считаем при рендере** (или `useMemo`), не в `useEffect` + `setState`.
- **`useEffect`** только для синхронизации с внешним миром (подписка, таймер, DOM-API), всегда с cleanup. Подписки на Firestore через `useSubscription`.
- Ключи списков стабильные (`id`), не индекс.
- Код переживает StrictMode: эффекты идемпотентны.
- Состояния данных обрабатываются через `QueryBoundary`: loading, error, empty, success. Нельзя оставить экран без любого из состояний.
- Формы: React Hook Form (`useForm`) + Zod-резолвер (`@hookform/resolvers/zod`, нативная совместимость с Zod 4). Используется компонент `components/ui/form.tsx` (`Form`, `FormField`, `FormItem`, `FormLabel`, `FormControl`, `FormMessage`), обеспечивающий автоматическое связывание `id`, `htmlFor`, `aria-describedby` и `aria-invalid`. Схема формы выводится из доменной схемы или определяется в `formSchemas.ts`. Сообщения схем — ключи i18n, транслируемые хелпером `translateValidationMessage(t, message)`.
- Доступность: у иконок-кнопок `aria-label` (из i18n), видимый фокус, семантические теги, клавиатурные сценарии.
- Мемоизация (`memo`, `useCallback`) только при измеренной проблеме.

Плохо:

```tsx
const [total, setTotal] = useState(0)
useEffect(() => { setTotal(sum(transactions)) }, [transactions])
```

Хорошо:

```tsx
const total = useMemo(() => sumByType(transactions, 'expense'), [transactions])
```

## 6. Данные и Firestore

- В UI и хуках нет импортов `firebase/firestore`. Только через repository.
- Repository-функции принимают `uid` явно, возвращают доменные типы (не `DocumentSnapshot`), бросают `AppError`.
- Converter создаётся общей фабрикой `createConverter(schema)`, пути коллекций берутся из одного модуля.
- Мутации, затрагивающие баланс, всегда идут через `writeBatch` и `balanceDeltas`.
- Запросы только из `02-data-model.md` (§6). Новый запрос или индекс означает остановку и согласование.
- Поле отсутствует, а не `null`. Очистка через `deleteField()`.

Плохо: запрос `getDocs(query(collection(db, ...)))` прямо в компоненте.
Хорошо: `const { data } = useTransactions(month)`.

## 7. Деньги, даты, числа

- Деньги: целые minor units. Операции только через `lib/money.ts`: `parseMoneyInput`, `formatMoney`, `toMinorUnits`, `fromMinorUnits`, `signedAmount`.
- Форматирование: `Intl.NumberFormat` с локалью и валютой профиля.
- Дата транзакции: строка `YYYY-MM-DD`, операции через `lib/dates.ts`. `new Date('2026-09-01')` для календарной даты запрещён (сдвиг по часовому поясу).
- Сравнение денег и дат через функции домена, не ручная арифметика в компонентах.

Плохо: `(amount / 100).toFixed(2)` в JSX
Хорошо: `<MoneyText amount={tx.amount} type={tx.type} />`

## 8. i18n

- Любой видимый текст (включая `aria-label`, `placeholder`, `title`, toast, ошибки) через `t('...')`.
- Ключи в обоих языках (EN и RU) добавляются **в одном коммите**. Нет ключа в RU означает незавершённая задача.
- Плюрали через i18next (`count`), не через `if`. Для русского три формы.
- Даты: date-fns с локалью. Числа и валюты: `Intl`.
- Повторяющийся текст использует один ключ (`common.actions.save`), а не копии.

## 9. Обработка ошибок

- Repository: ловит ошибки Firebase, бросает `AppError` с кодом.
- Hook: отдаёт `error` или обрабатывает мутацию в `.catch`.
- UI: показывает понятный i18n-текст по коду ошибки. Без «Something went wrong» на все случаи и без тихого проглатывания.
- Никаких пустых `catch {}`. Логирование только осмысленное (не `console.log` в коммитах).
- Ожидаемые состояния (пусто, офлайн, нет прав) это UI-состояния, не исключения.

## 10. Комментарии и документация кода

- Комментарий объясняет **почему**, а не **что**. Если нужно объяснять «что», переименуй или вынеси.
- Комментарии в коде на английском, короткие. Публичные функции `lib/` могут иметь краткий JSDoc с примером.
- Не оставляем закомментированный код и `TODO` без ссылки на задачу.

## 11. Структура файла

Порядок: импорты, константы, типы, основная функция или компонент, вспомогательные (приватные) функции. Импорты группируются: внешние, `@/` алиасы, относительные. Порядок обеспечивает линтер или Prettier-плагин.

## 12. Тесты (кратко, полная стратегия в `05-testing-strategy.md`)

- Тестируем поведение, не реализацию. Запросы к DOM по роли и тексту (Testing Library).
- Domain-функции покрываются unit-тестами плотно (деньги, даты, агрегации, CSV, `balanceDeltas`).
- Фабрики тестовых данных в `src/test/`, без копирования объектов по файлам.
- Тесты называются по поведению: `it('rejects amount that is not an integer')`.
- Баг сначала воспроизводится тестом, затем исправляется.

## 13. Git и PR

- Ветка на фичу, PR даже в одиночку (CI и preview).
- Коммиты Conventional Commits на английском: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`. Один коммит на задачу T.
- Squash merge. Заголовок PR в формате коммита.
- PR содержит: ссылку на спеку, скриншоты UI (desktop, mobile), результат `verify`.

## 14. Чеклист ревью (используется и агентом, и человеком)

**Архитектура:** границы слоёв соблюдены, нет импорта `firebase/firestore` вне repository, фича использует чужую только через `index.ts`.
**DRY и maintainability:** нет дублирования стилей, текстов, логики. Есть ли готовый компонент в `common`? Нет магических значений. Размеры в норме.
**Данные:** деньги в minor units, даты строкой, `balanceDeltas` используется, нет `null` в документах, запросы из `02-data-model.md`.
**UI:** есть loading, empty, error, offline. Mobile. Тёмная тема. Доступность (aria, фокус, контраст).
**i18n:** нет жёстких строк, ключи в EN и RU, плюрали корректны.
**Надёжность:** подписки отписываются, ошибки обрабатываются, нет гонок при StrictMode.
**Безопасность:** нет секретов, rules не менялись без согласования, CSV-экспорт экранирует формулы.
**Тесты:** acceptance criteria покрыты, тесты проходят, `verify` выполнен.
**Запрещённое:** нет legacy-паттернов из `AGENTS.md` (раздел 11).
